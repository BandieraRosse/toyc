# SC7 提交级证据表

## 使用说明

本表为 [SC7 前史](../periods/sc7.md) 提供可复核依据，不承担连续叙事。提交号均属于公开仓库
`WHU-SC7/SC7`；核查时应固定完整提交对象，并同时查看父提交、变更路径和内容。

“同期陈述”主要来自 commit message 或当时 README，只证明提交者当时作出过该声明；“代码记录”
表示已确认相关改动进入 Git，不自动证明功能通过独立复现；“作者回忆”是事后口述。

## 关键冲突与不确定项

### 动态链接

- `64d9400`（2025-06-17）的提交说明记录：修改 `PROT_NONE` 权限、针对异常地址加入特殊映射，
  并宣称 RISC-V glibc dynamic 可以运行。
- `8a698fc`（2025-06-18）记录解释器选择继续完善，同时说明 LoongArch glibc 动态链接仍有问题。
- `5ecb529`（2025-06-18）由队友提交，说明通过增加映射长度等改动使 LoongArch glibc 动态链接
  成功。

对象级复原表明，`0x000000010000036e` 最早是 `a0f069c` 提交说明中的 RISC-V fault address，
`64d9400` 新增的故障日志又保存了同一数值；触发 ELF 不在仓库中，不能证明 glibc 如何算出它。
`64d9400` 把该未对齐地址传给会执行 `PGROUNDDOWN` 的 `mappages`，实际映射
`[0x100000000, 0x100001000)` 一页，权限为用户 R/W/X 并带 dirty 位。物理页来自
`pmem_alloc_pages(1)`，调用处没有清零或写入；该提交还把 RISC-V `PROT_NONE` 改成 R/W。

`8a698fc` 明确区分解释器，并称剩余故障是 LoongArch glibc 在 mmap 页尾清零时的 kernel trap；
这与 RISC-V 固定高页、musl 早期成功是三条不同问题线。`5ecb529` 曾无条件令 mmap 长度增加一页，
注入 `LD_LIBRARY_PATH` 并改变读取/清零逻辑，但次日 `7774309` 就撤销额外一页，`59d0544` 还记录
RISC-V 多分配一页会触发 futex 异常。固定高页随后仍被 `6a35a7c` 特判复制给 RISC-V clone
子进程；后续 VMA/lazy-load 重构后的树中该常量才消失，没有一条可孤立归因的删除提交。因此
`5ecb529` 没有替代或删除 workaround。本轮没有比赛镜像与对应动态 ELF，所有“正常”“成功”仍
只是 commit message 的同期声明。

### 多核

- `a960728` 记录 RISC-V 多核启动。
- `8f3ca98` 宣称 RISC-V 多核可以运行 basic。
- `db40a0b` 继续修复多核服务进程输出。
- `9a3465e` 宣称 LoongArch 多核启动并运行 basic，但默认仍为单核。
- 作者事后回忆，多进程并发时出现难以定位的锁问题和随机错误，可能涉及栈或共享变量；由于内核并发
  问题定位成本过高且多核不是强制要求，团队最终放弃该任务。

两类材料并不矛盾：阶段性 basic 成功不等于多进程压力下稳定，最终放弃也不否定窄测试曾经通过。
`a960728` 的 `run_sbi` 为 3 核；`8f3ca98` 的 RISC-V basic 声明对应 2 核，并加入磁盘锁；
`db40a0b` 又修改服务进程的一页缓冲、输出和通知时机。`9a3465e` 宣称 LoongArch 两核 basic 成功，
却同提交保持 LoongArch 默认 `-smp 1`，并注明 PID 模 128 的输出碰撞边界。随后 `787bc9a` 给
pmem/vmem 加锁并注释调度锁 panic，`f978dbc` 为恢复单核文件写入调整 VFS/磁盘锁并暂删 inode 锁；
提交日志仍记录 BusyBox/libctest 偶发 `sched error`。到 `pre_final1` 和现场代码，常用 QEMU/
`run_sbi` 均已为单核。仓库没有保存可复现的随机失败日志；栈、共享变量仍只是作者回忆中的怀疑。

### VisionFive SD 驱动来源

`74aee85` 首次加入两个头文件和四个 C 文件；`df580fe` 第二次移植时六个文件逐个 blob 完全相同，
变化在重新接入主线的启动与虚拟内存代码。新增文件没有版权头或来源 URL，但注释反复写“按照 Rust
驱动的逻辑”“参考 Rust 版本”。全历史中没有这些 blob 的更早提交。因此可确认两次 SC7 接入，
结合作者口述可记录底层初始化/读写文件由队友提供；不能称六文件全为作者原创，也不能断言具体外部
源项目。

### 外部继承与 XN6

README 的模块声明是：XV6 对应 RISC-V HAL 与 HSAI trap；XN6 对应 LoongArch HAL 和 HAL/HSAI
思想；AVX 对应部分 syscall/VMA；lwext4 是直接移植并局部扩展的 ext4；Linux 对应 VFS 思想和
JHash。源码保留 XV6 trampoline 替换记录、lwext4 原版权头和 Linux SPDX/版权头。故不能把整个
内核笼统称作基于 XV6，也不能把直接移植算作个人原创；尚缺上游快照，不能逐文件量化改写比例。

最早的 `doc/SC7_log/2025_3_21.doc` 构建路径明确叫 `C_XN6_rewrite`，LoongArch 使用 g++ 链接，
RISC-V 已用 gcc/ld；提交日志后来记录“把所有 xn6 改成 sc7”。这是最初进行 XN6 C/RISC-V 重写
的同期证据。当前缓存没有 XN6 对象，尚不能核定文件相似度、C++ 使用程度及“2024 二等奖”记忆。

### SC7 到 Tinylibc

SC7 `d2363da` 的 `user/include/Tinylibc/` 与 Tinylibc 根 `fce216c` 都有 29 个相同路径：26 个
blob 完全相同，只改 `README.md`、`tlibc_commit_log.md`、`项目计划.md`，没有源码增删改名。这是
“只修改三个 md 文件”的准确含义。根树仍只有 RISC-V；三小时后的 `7586050` 才加入 x86_64
syscall/ABI 适配并声明在 PC 运行，`19b683e` 再整理 freestanding 链接。

### 开发日志与赛事评价

SC7 `doc/commit_log.md` 共 1760 行，从 3 月连续到现场赛；SC7 的 `tlibc_commit_log.md` 在分离前
为 198 行，Tinylibc 根提交原样继承并追加分离记录，现有历史继续到 417 行。何时不再由作者亲自
维护无法从提交者元数据判断，仍需 agent 会话或访谈。

oscomp 的获奖作品汇总只列 2025 年一等奖八队，没有二等奖或完整排名，不能据此确认 SC7 奖级、

## 作者补充（2026-09-15）

- 初赛由作者搭建 SC7 原型，并承担大部分底层硬件规范相关工作；队友接手时已经得到一个接近 XV6
  能力的双架构内核。初赛后期作者解决部分动态链接问题并参与讨论，队友解决另外部分；作者主观估计
  自己还分担了约三分之一的 BusyBox、libctest 等测试工作。
- 决赛阶段一，作者主观估计分担约三分之一 LTP 任务，并负责真实开发板调试和驱动开发。
- 决赛现场赛，作者负责上板和测试；队友改进动态链接系统调用后，由作者在板上启动验证。现场还处理
  了 U-Boot 启动后必须主动清零 BSS、为多个位置补充显式初始化，否则发生内存错误的问题。
- 团队最初考虑把上一届 LoongArch 项目 XN6 移植到 RISC-V；作者认为其中 C++ 的 `new`、虚函数、
  类等抽象过重，主张使用 C，并参考 XV6 自己写出原型。作者记得 XN6 是 2024 年内核实现赛获奖
  项目，但奖项等级只记得“似乎是二等奖”，尚未外部核实。
- “前期基础系统调用约一半、后续新增系统调用约三分之一”只是作者的主观感觉，不适合作定量统计。
- 作者没有参与文件系统实现，主要使用队友提供的接口完成上层工作。
- LoongArch 虚拟化和后期动态链接主要由队友推进；LoongArch VirtIO 磁盘后来另有一次以作者为主、
  队友协助的修复，提交待定位。
- VisionFive SD 驱动所依赖的可用初始化、读取、写入函数及文件由队友提供，对驱动落地至关重要；
  作者负责移植、接入和调试。
- 作者不能确定 `64d9400` 所处理问题的真正原因。当时对 libc/glibc 理解有限，也没有使用 Claude
  Code 或 Codex；因定位成本过高，选择 workaround 后不再深挖，是一次工程决策。
- 比赛后继续写 `tlibc`，是因为仍对 C 感兴趣，但内核太难、成果周期不明确，用户态更容易推进。
  最初仍在 SC7、QEMU 和非 x86_64 架构上运行，后来为了在原生 Ubuntu 直接运行才迁向 x86_64。
- 没有延续 SC7 的 Git 历史，是因为 SC7 不支持 x86_64；作者认为旧架构历史对新的 libc 主线没有
  保留意义。
- SC7 阶段主要由作者自己编写、编译和调试，通过网页端 AI 提问、查文档和提炼重点；这一过程带来
