## Q1：Tinylibc 的起点、重启与编译器动机

第一轮问题为：

1. 你认为“Tinylibc 手写时期”的起点和终点分别是什么？
2. 独立后最初想把 Tinylibc 做成什么：学习项目、可实际使用的 libc、自包含用户态环境，
   还是别的目标？
3. 2026-06-30 为什么突然开始写 C 编译器？直接触发事件是什么？
4. 最早的编译器代码是怎样设计出来的？哪些来自自己构思，哪些参考了书籍、网页、其他
   编译器或 AI 原型？
5. 从网页问答转向 Claude Code 等 coding agent，大致发生在什么时候？开发流程具体发生了
   什么变化？

### A1（原文）

我给出关键信息的回答：

1. 起点是一个软件工程的课程，我把这个作为课程作业，也是我感兴趣的。终点分了几个，
   第一次大概是26年初的中断，那时候手写遇到了挺大的困难，最终停在了几个命令行交互程序
   top之类的。再次启动是pthread时期，那次终于让多线程成功跑起来了，虽然有小瑕疵。然后我把
   pthread的一点改动作为毕业论文。这时我也想写网络程序，和音频程序。音频程序很难在网页端
   ai的辅助下，自己手写。我最后卡在这一步，写了一些老网络程序，没有成功写出来自包含库的
   音频程序。这个时候开始接触claude code + deepseek api，但是没有大规模应用，网络老程序也是
   主要自己手写的。网页端ai用于查syscall用法，以及一个简单程序，正确调用syscall的参考原型。
   然后应该又暂停了一段时间，Tinylibc最后启动，是想做编译器项目，这时也用cc+deepseek改写了
   部分Tinylibc内容，并且大规模使用coding agent。不过初期很快遇到了困难，之后就逐渐转到
   ToyCCompiler了。
2. 最初是一个探索，我那时对操作系统内核有一定了解，但是对libc了解较少。立项是出于好奇，
   也刚好作为课程作业。从那时开始就是我自己写了，时不时和别人分享一下。对，最初是学习，
   是好奇，也是喜欢。当时并不了解，所以没有多大的野心，因为也不知道能做到什么程度。
3. 写C编译器是我一直以来的想法，长期的，一个愿望。因为我感觉C语言很酷，底层，比较简单，
   古老。然后最初的C编译器应该是汇编写的，应该是PDP-11吧，我感觉用汇编写C编译器太酷了，
   然后汇编编译器自举，再用核心子集写出完整的C编译器，然后C89。我相信很久以前，主流方式就是
   用C编译器，那在当年应该是很强大的。我还喜欢C语言的简介，我可以看到每一步在做什么，抽象
   很少，函数调用规范，栈管理，所有的计算机细节都能感受到。直接触发事件应该是用了claude code
   + deepseek api吧，让我感觉效率大幅提高了，以前的开发效率是不敢想的。
4. 说来惭愧，是让deepseek api在claude code自行设计的。我提了简单但核心的限制，要所有文件和
   依赖都在Tinylibc中，不要标准库。然后deepseek api自行设计了这个框架，当时不完善，但是后来
   沿用了这个架构。
5. 可以具体查阅git记录，是在今年大概6月吧，6月底就高强度使用了。之后我就主要思考和写prompt
   了，不自己写代码和调试了。以前都要自己写和调试。

## Q5：为什么重新统一为 Toyc

问题涉及为何不继续分仓、双向移植的含义、“two parents”、改名和只迁移部分应用。

### A5（原文）

toyc编译器最初的目的就是编译我自己的Tinylibc的库，取代部分gcc的功能，没有理由在
ToyCCompiler成熟之后，还分家，还分两个仓库，需要统一，toyc是借着这个统一机会起的新名字，
比之前更好。

2. 这是现实的困难，虽然toyc自举了，但是编译Tinylibc还是有一点距离，这段时间在探索让toyc
   编译器成功编译Tinylibc的方式，最终选择的方式是在toyc中新建针对各个Tinylibc的lib模块的
   测试，然后逐个完成。我认为这是成熟的方式，比之前尝试一下子融合，然后toyc编译器马上成功
   编译lib更成熟可行，更现实。
3. 我印象不清楚了，需要你列出更多信息。
4. 对，有这个意思，成为一个有点功能的玩具了，也包含比较完整的C生态了。
5. 我印象不深了，只记得，有一部分app是难迁移的，当时先迁移了好验证的，然后有些老程序，
   我感觉意义有限，就留在老仓库中了。

在看到同期 “two parents” 周边材料后，作者补充：

认可。我觉得这标志着toyc的成熟，standalone的目标。只有lib的standalone是不完整的，但是有了
standalone的编译器之后，这个toyc的生态就形成闭环了，理论上它就真的可以创造自己，并且创造
一切了，这是伟大的进步。只要时间足够，当然工程上未必可行，不会有人做这个。我后续更新了一段
时间toyc，不过为了效率也常用gcc了。

## Q6：从逐行掌握到风险驱动理解

问题被重新表述为：面对陌生系统软件和个人时间限制，开发方式如何限制可达规模；使用 agent 后，
作者放弃和保留了什么。

### A6（原文）

好问题。我的回答是：在我事先没有写过，不知道这些软件的知识的时候，使用网页端ai的辅助，自己
开发测试，只能做到早期Tinylibc的程度，做standalone的C编译器不现实，很困难。所以，**在没有
经验，第一次做的情况下**，对我来说不可能做到ToyCCompiler的程度，以及toyc的程度，现在程度的
任务，到Tinylibc的程度会是一个大概率的事情。这是现实条件下的取舍。我意识到软件就是这么复杂，
要效率，要做我想做的事情，就要改变方式，放弃对每个细节的掌握，利用agent和ai。

追问后，作者补充：

1. 是逐渐明确的，不过我早期就能感受到写standalone C编译器不现实。

   敏感，尤其是已经有经验的。

   接受的。抓住主要部分，继续向前。因为完全掌握，就是有成本的，到达一定程度的边际成本不划算，
