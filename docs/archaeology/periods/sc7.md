# SC7 前史

## 研究范围

SC7 是作者在 2025 年参加操作系统内核比赛时参与的三人团队作品。它不是 Tinylibc、
ToyCCompiler、Toyc 这条个人项目主线的简单第一版，但构成了理解其底层知识、用户态设施和
C 项目经验来源的重要前史。

## 赛事时间背景

外部赛程资料显示，2025 年内核实现赛道初赛作品提交截止为 2025-06-30；决赛相关测试和现场
环节集中到 2025-08-20 左右。不同通知对决赛阶段的切分略有差异：一份赛程将决赛阶段列为
2025-07-12 至 2025-08-12、再进入 8 月 13 日起的现场阶段；比赛平台则列出 2025-07-23 至
2025-08-20 的决赛阶段 1，并将 QEMU/开发板测试安排在 8 月 20 日。这里仅用来辅助划分提交
阶段，不把平台阶段直接等同于队内分工。

## 已确认事实

- 仓库远端为 `WHU-SC7/SC7`，主分支本轮观察到 620 个提交。
- 根提交 `ec37618` 日期为 2025-03-23，说明首次版本支持 RISC-V 与 LoongArch 双架构 UART 输出。
- README 将 SC7（martCore7）描述为基于 MIT XV6、使用 C 开发、支持 RISC-V 与 LoongArch 的
  教学操作系统，并列出三名学生成员和指导老师。
- 仓库按初赛、决赛一阶段和决赛现场赛保存分支及文档。
- 功能涉及进程与线程、物理和虚拟内存、VFS/ext4、系统调用、信号、procfs、多核启动与用户程序。
- 决赛现场赛文档记录了动态链接、符号链接、文件位置同步、物理开发板适配，以及通过拆分提交
  降低复杂度的经验。
- 仓库存在远端 `tlibc` 分支；其与 Tinylibc 根提交的准确关系尚未核对。

## 作者提交记录线索

Toyc 与 SC7 中的多个历史提交身份已由作者确认属于同一作者，本文不保存具体姓名、邮箱或账号标识。
这些身份记录可以归并分析；提交作者仍只证明提交归属，不等于该提交中的每一部分都由作者独立完成。

按提交说明和变更路径，作者可确认或高度可信地负责以下工作线：

- **双架构底层与启动链路**：早期主导 RISC-V 用户态进入、trap/异常返回和系统调用框架，并参与
  LoongArch 方向的早期框架工作，代表提交为 `19e560d`、`ecf7de8`、`fb5ef68`、`564105d`、
  `e21c43e`。但 LoongArch 虚拟化用户态最终由队友推进，不能写成作者独立解决。
- **设备、平台和多核尝试**：主导 RISC-V SBI、VirtIO 磁盘、LoongArch PCI/VirtIO、时钟中断及
  多个板端适配。多核部分确实写过启动、调度和服务进程代码，但最终没有成功，不能表述为“完成
  多核适配”；相关提交包括 `df5eeef`、`1ae3eba`、`d31e2c6`、`9df96f0`、`8f3ca98`、`a960728`。
- **文件系统接口与文件相关系统调用**：实现或修复 `getcwd`、`mkdirat`、`chdir`、`getdents64`、
  `unlink`、`link`、`symlink`、`lseek`、`pwrite64`、`prlimit64` 等，并处理 ext4 上层接口、路径
  和错误码，代表提交为 `e86f184`、`e23f00a`、`8436f13`、`f0d02af`、`57567e9`、`4c92f0f`。
  但初始 ext4/lwext4 移植由队友完成，作者当时也尚未真正理解 ext4；后续 VFS/ext4 的重构和
  修复还包括队友提交，不能统一归为作者成果。
- **真实硬件适配与测试**：推进 VisionFive 和 2K1000 的启动、文件系统接入、虚拟内存和板端调试，
  例如 `974c487`、`460709e`、`7d99e47`、`5bbdf4d`、`d389233`、`df580fe`。其中 VisionFive
  板载 SD 存储驱动的主要移植提交为作者的 `74aee85`/`df580fe`，但作者确认该部分得到队友帮助，
  提交记录本身无法量化协助范围。
- **LoongArch 虚拟化协作**：作者提交过 LoongArch 的 PCI/VirtIO 磁盘路径（`407f2fe`、`9df96f0`）
  和相关调试，但作者确认没有解决 LoongArch 虚拟化问题；用户态虚拟内存、陷阱和从磁盘执行 ELF
  的关键推进来自队友。因此这里应记录为队友主导、作者参与协作，而非作者独立负责。
- **Tinylibc 用户态生态**：在 `origin/tlibc` 上完成库构建整理、Shell、`ls`/`touch`/`cat`/`rm`/
  `echo`/`pwd`/`cd`/`mkdir`/`rmdir`/`cp`/`mv`/`help` 等命令，以及对应的 `read`、`openat`、
  `fstat`、`fork`、`wait`、目录和删除操作；代表提交为 `5aa1cb2` 至 `d2363da`。

SC7 还有两条主要队友提交线，合并提交也使用过团队账号。作者回忆：前期基础系统调用约一半由
作者完成，后续新增系统调用中作者约完成三分之一；最关键的虚拟内存和文件系统由队友承担很多，
后期动态链接问题也主要由队友推进。作者后期重心转向设备适配，并分担一部分系统调用功能。
这些比例是作者回忆中的粗略估计，分母和阶段边界仍需进一步定义。

作者还回忆，约 2025 年 6 月中旬曾独立处理过一次 glibc 动态链接启动问题：程序访问一个启动
时尚未通过 `mmap` 映射的异常地址，作者排查后采用直接映射该地址但不写入内容的办法，使程序
能够启动。对应提交线索为 `64d9400`，但后续 `mmap`、虚拟内存和动态链接工作已交由队友推进，
作者在决赛阶段也未继续负责这些部分；具体代码演化仍需逐提交复原。

## 按提交顺序推断的分工

以下分段依据提交密度、变更主题和作者回忆，不直接等同于比赛官方阶段：

- **早期原型与基础框架（2025-03 至 2025-04 上旬）**：作者强烈主张用 C 开始项目，理由是希望
  自己掌控系统实现，并快速给出原型。提交记录显示作者主要推进双架构启动整理、RISC-V 用户态、
  trap 返回、基础系统调用、进程入口和部分设备路径；LoongArch 的虚拟化用户态尚未由作者解决。
- **系统能力扩展与协作整合（2025-04 中旬至 2025-06）**：作者继续推进 RISC-V SBI/VirtIO、
  LoongArch PCI/VirtIO、时钟和用户态接口，并分担一部分文件相关系统调用。初始 ext4/lwext4 由
  队友移植，虚拟内存和 LoongArch 用户态虚拟化由队友推进，动态链接相关问题也主要由队友解决。
- **后期适配与 Tinylibc 分支（2025-07 至 2025-10）**：作者重心转向 VisionFive/2K1000、SD
  存储和板端适配，同时继续完成部分系统调用，并在 `origin/tlibc` 上发展 Shell 和 Tinylibc。
  多核代码在这一阶段持续出现，但最终没有成功运行，不能计为已完成能力。

还需要补齐的不是“谁提交了代码”，而是：比赛官方阶段与上述时间段的对应关系、作者所说基础系统调用
比例的统计口径、板载存储驱动中队友帮助的具体部分，以及动态链接问题的关键决策和最终修复归属。

## Git 记录核对结论

### C 原型与早期基础

- `ec37618`（2025-03-23）是双架构 UART 原型；`cae8d60`、`bb7d03b`、`8e59241` 继续推进
  Makefile/硬件抽象、printf 和进程模块。结合作者回忆，可以确认作者在项目最初推动 C 路线并快速
  形成原型，早期主线重点是启动、进程和用户态基础，而不是 ext4。
- `19e560d`、`ecf7de8`、`fb5ef68`、`564105d`、`e21c43e` 显示作者连续推进 RISC-V 用户态、
  trap 返回和基础系统调用，并开始处理 LoongArch 用户态框架。这些提交支持“作者主导早期框架”，
  但不支持“作者独立完成双架构虚拟化”。

### 虚拟内存、文件系统与动态链接的分工

- `02649e8` 引入 lwext4、VFS_EXT4 和 VFS；`c69bb28`、`3b3688e` 继续重构 ext4/VFS。它们
  属于队友的核心文件系统工作，作者在该阶段并未掌握 ext4 内部实现。
- 作者的 `e86f184`、`e23f00a`、`03855b4`、`f0d02af`、`57567e9`、`3df36c0`、`4c92f0f` 等
  提交，主要集中在文件系统之上的路径处理、系统调用、错误检查和测试适配；应表述为“使用并扩展
  队友提供的文件系统基础”，而非“负责 ext4”。
- `61bebb2`、`217dade`、`5ecb529`、`127fca0`、`2fa9e37`、`6cd42ce`、`8f721c0` 等提交
  显示队友持续推进 LoongArch/通用虚拟内存、lazy load、VMA 和动态链接；`b3a44a8`、`a04b0d0`
  进一步完成 LoongArch 从磁盘读取并执行 ELF 的关键路径。这支持“LoongArch 虚拟化由队友成功
  推进”的回顾结论。
- `64d9400`（2025-06-17）是作者在 glibc 动态链接早期针对异常地址 `0x000000010000036e`
  的直接映射 workaround；紧接着 `8a698fc` 仍记录 LoongArch glibc 动态链接问题，`5ecb529`
  （2025-06-18）记录队友通过增加映射长度等方式解决。后续动态链接、mmap 和虚拟内存不应归为
  作者负责。

### 设备适配与多核

- `d31e2c6`、`407f2fe`、`9df96f0` 显示作者搭建并验证 LoongArch PCI/VirtIO 磁盘设备路径，
  但这不等于作者解决了 LoongArch 用户态虚拟化；后者由队友的 `b3a44a8` 等提交完成关键推进。
- `74aee85`（2025-07-31）和 `df580fe`（2025-08-20）新增完整的 VisionFive SD 驱动 C 文件，
  包括 `sdio_cmd.c`、`sdio_ops.c`、`sdio_utils.c` 和 `vf2_sd_timer.c`，提交说明记录虚拟内存下
  读写测试通过。Git 能确认作者提交并接入了可用驱动，不能从提交对象判断队友协助的具体范围。
- `a960728`、`8f3ca98`、`9a3465e`、`db40a0b` 等提交确实包含多核启动、调度和服务进程代码，
  部分提交说明使用“运行成功”字样；但作者回顾最终多核没有成功，故历史文档应同时保留“当时提交
  的成功宣称”和“最终能力未稳定”的差异，不能把它列为已完成模块。

## 与后续主线的可能联系

以下只是研究方向，不能在完成代码对照前写成确定的继承关系：

- 系统调用封装、用户态入口、C 库与 shell 经验可能成为 Tinylibc 的直接技术背景。
- 双架构内核、物理板和 QEMU 调试可能影响了后来对 ABI、ELF、freestanding 运行时的理解。
- 决赛文档已经表现出“拆分复杂问题、用连续提交逐步恢复能力”的工程方法，值得与后续编译器
  密集修复过程对照。

## 边界原则

SC7 是团队成果。后续文档引用其代码与成果时，必须区分团队整体成果、外部参考项目、成员分工
和作者个人完成的部分；不能因为 Tinylibc 由作者延续，就把 SC7 的全部工作归入个人项目史。
