# SC7 前史

## 本章定位

SC7（martCore7）是作者在 2025 年参加操作系统内核比赛时参与的三人团队作品。它不是
Tinylibc、ToyCCompiler、Toyc 个人项目主线的简单第一版，但提供了这条主线最早的操作系统、
用户态接口和 C 工程经验。

本章只保留已经能够形成叙事的结论。逐提交记录、证据性质和未解决的冲突见
[SC7 证据表](../evidence/sc7.md)；尚待作者回答的问题见[关键问题台账](../questions.md)。

## 项目与赛事背景

SC7 README 自称项目“基于 MIT XV6”、使用 C 开发并同时支持 RISC-V 与
LoongArch，同时列出三名学生成员。但“基于 XV6”只是仓库的总括性自述：仓库还明确列出
XN6、AVX、lwext4 和 Linux 等参考或移植来源，现有核查也没有完成各来源的逐文件归属；
因此，讨论个人贡献时必须继续区分自行设计、参考实现适配、第三方库移植和团队协作。

官方时间线与仓库开发阶段不是同一套划分：初赛于 2025-06-30 结束，线上决赛作品在 8 月中旬
提交，线下决赛与答辩集中在 8 月 20 至 21 日；比赛平台另将 2025-07-23 至 08-20 标为“决赛
阶段 1”。仓库则保存 `preliminary_contest`、`pre_final1`、`offline` 等阶段分支。下文以代码演化
划分阶段，不把分支名或平台日期直接当作队内分工证据。三个赛事分支名后来已从远端删除，但合并
对象仍能固定初赛终点 `bcfab95` 与决赛阶段一终点 `b927bc1`；现场赛由多条成员线汇合，原
`offline` tip 尚不能唯一恢复。现场文档把起点误写成不存在的 `28aab57`，其元数据实际对应
`3c6e528`。

## 按赛事阶段的职责

以下分工主要来自作者 2026 年 9 月 15 日的回忆，提交对象只能交叉确认其中部分任务和改动进入仓库，
不能还原口头讨论、共同调试或未提交的工作。因此本节是已用 Git 尽可能约束的口述分工，
不是从提交数量换算的工作量结论。

### 初赛

作者搭建了 SC7 的最初原型，并承担了大部分与底层硬件规范相关的工作。随着原型发展，队友接手时
已经得到一个能力接近 XV6、支持双架构的内核基础。初赛后期，作者解决了一部分动态链接问题，也与
队友共同讨论；其余关键问题由队友继续解决。测试工作方面，作者估计自己分担了约三分之一，包括
BusyBox、libctest 等测试的接入、运行和问题处理。这个比例属于作者对工作量的回顾，不作精确统计。

### 决赛阶段一

作者估计自己分担了约三分之一的 LTP 任务，同时把主要精力放到真实开发板调试和驱动开发。这里的
“三分之一”同样是主观工作量概括；具体用例与提交仍以 Git 和测试记录为准。

### 决赛现场赛

作者主要负责上板和现场测试。队友改进动态链接相关系统调用后，作者负责在开发板上启动并验证。
现场暴露出 QEMU 或普通启动环境中不明显的初始化假设：例如经 U-Boot 启动后，内核不能依赖 BSS
区域天然为零，必须主动清零 BSS，并补充多个结构体和变量的显式初始化，否则会在不同位置出现内存
错误。对象 `524e2ef` 确认作者同时加入链接脚本 BSS 边界、启动入口清零，以及 buffer cache、
file vnode、filesystem、inode 等显式初始化，并继续承担现场验证。

## 开发过程

### C 原型与 RISC-V 用户态基础

2025 年 3 月下旬，SC7 从双架构 UART 原型起步。团队起初考虑把上一届 LoongArch 内核项目 XN6
移植到 RISC-V；作者不喜欢其中 `new`、虚函数和类等 C++ 抽象，认为对当时的目标过重，因而主张
改用 C，并参考 XV6 自己写出最初原型。提交记录显示，作者随后连续推进 RISC-V 用户态进入、trap
返回、重复系统调用、系统调用参数获取以及内核与架构相关代码的分离。

这些材料支持“作者主导了早期 RISC-V 用户态和系统调用框架”，但不能支持“作者独立完成了双架构
用户态”。LoongArch 用户态虚拟内存、陷阱处理和从磁盘执行 ELF 的关键路径后来由队友推进。

### 文件系统基础与系统调用扩展

2025 年 4 月下旬，队友引入 lwext4，并建立 VFS_EXT4 与 VFS 层；5 月又继续重构相关接口。作者
当时并未掌握 ext4 内部实现，其工作主要位于文件系统之上：实现或修复 `getcwd`、`mkdirat`、
`chdir`、`getdents64`、`unlinkat`、`linkat`、`symlinkat`、`lseek`、`pwrite64`、`prlimit64` 等
系统调用及其路径、错误码和测试适配。

因此，本项目史把文件系统实现记为队友工作。作者确认自己没有参与文件系统实现，主要是使用其接口
完成上层系统调用、路径和测试适配，不笼统写成作者“负责 ext4”。作者曾以“早期约一半、后续约
三分之一”描述自己承担的系统调用，但现已确认这只是主观感觉，不作为定量历史结论。

### 动态链接与 LoongArch 协作

2025 年 6 月，团队连续处理 musl/glibc 动态链接、VMA、`mmap` 和 lazy load。作者在 `64d9400`
中针对 RISC-V glibc 动态链接异常地址加入了特殊映射，提交说明宣称由此可以运行。源码确认未对齐
地址被向下取整，实际映射 `0x100000000` 起的一页，权限为用户 R/W/X；调用处没有写入或清零页面。

此后作者继续整理 musl/glibc 解释器选择，但 LoongArch glibc 动态链接仍有问题。队友次日提交
`5ecb529`，通过临时增加一页映射长度、环境变量和读文件逻辑等改动，宣称 LoongArch glibc 动态链接
成功；额外一页次日即被撤销，并没有替代 RISC-V 固定高页 workaround。后续 VMA、lazy load 和
虚拟内存工作也主要沿队友提交线推进。作者事后不能确定特殊地址问题的根因：
当时对 libc，尤其是 glibc，理解有限，也没有使用 Claude Code、Codex 一类 coding agent；在定位
成本很高的情况下，以 workaround 先恢复运行、没有继续追查，是一次有意识的工程取舍。

因此，这一阶段应描述为作者参与早期诊断和局部修复、队友主导后续虚拟内存与 LoongArch 动态链接
收敛，而不是把完整成果归给任何一次单独提交。另一次 LoongArch VirtIO 协作问题可定位为队友在
`92ccdea` 记录 glibc 读盘忙等待，作者以 `530de36`、`02a1167` 连续调整等待上限和忙等逻辑；源码
不能进一步量化协助方式。

### 多核尝试与真实硬件适配

2025 年 7 月的提交曾分别宣称 RISC-V 和 LoongArch 多核能够启动并运行 basic，用于服务进程和
调度的代码也确实进入仓库。但多个进程并发执行后，会出现难以稳定复现和定位的锁问题及随机错误；
作者当时怀疑过栈、共享变量等典型并发因素。由于问题发生在内核、定位成本很高，而多核又不是比赛
强制要求，团队最终停止投入并放弃了多核任务。因而“basic 曾阶段性成功”与“最终放弃多核”并不
矛盾：前者是窄测试结果，后者是稳定性和投入产出上的工程判断。

作者后期的重心转向 VisionFive 与 2K1000 等真实硬件。提交记录显示作者推进了启动、虚拟内存、
文件系统接入和板端调试，并两次提交 VisionFive SD 驱动移植，说明中记录了虚拟内存下的读写测试。
作者确认，队友提供了可用的初始化、读取和写入函数及相应文件，这是驱动能够落地的关键基础；作者
负责后续移植、接入和调试。Git 能确认提交和改动范围，但具体来源仍需通过文件内容和历史对象核对。

## 从 SC7 到 Tinylibc

比赛阶段结束后，作者仍然对 C 感兴趣，但认为继续写内核难度太高、成果周期不明确，于是转向更容易
获得反馈的用户态。SC7 的 `tlibc` 分支最初仍在 QEMU 和非 x86_64 架构上运行；`e2eef7f` 在
2025-09-24 以“TinyLibc 的第一次提交”为说明，随后逐步加入库构建、独立 `printf`、Shell、文件
操作命令以及相应系统调用封装。

后来作者希望程序能在原生 Ubuntu 和个人电脑上直接运行，不再依赖 QEMU；把整个 SC7 内核迁移到
x86_64 成本过高，因而选择把用户态项目分离并迁移。2025-10-17，独立 Tinylibc 仓库的根提交说明
项目从 SC7 分离并尝试支持 x86_64，早期仍保留了 RISC-V 部分，后来才停止使用。不过，SC7
`tlibc` 末端 `d2363da` 的 29 文件用户态子树与 Tinylibc 根树逐路径一致：26 个 blob 完全相同，
只修改 README、提交日志和项目计划三个 Markdown 文件，没有源码增删或改名。根树仍只有 RISC-V
代码；三小时后的 `7586050` 才加入 x86_64 适配并声明可在 PC 运行。作者事后解释，当时没有延续
原 Git 历史，是因为 SC7 不支持 x86_64，而自己判断旧架构历史对新的 libc 主线没有保留
必要。这说明当时的取舍，不等于那段历史在技术或考古上客观地“没有意义”。

## 对后续项目史的意义

SC7 可以确认提供了三类背景：系统调用与用户态入口的直接实践，双架构、QEMU 与真实开发板的调试
经历，以及在团队项目中处理文件系统、虚拟内存和设备边界的经历。SC7 `tlibc` 子树到 Tinylibc
根提交的代码继承已由 blob 对照确认；这些经验是否进一步影响了后来的 ABI、freestanding 运行时
和 Shell 设计，现有材料不足以继续确认。代码继承、知识连续和因果影响不应混为同一种关系。

按作者回忆，当时主要工作方式是自己编写、编译和调试，再通过网页端 AI 提问和查阅文档提炼重点；
他将真实硬件调试、Git、团队分工和亲手排错的积累概括为工程上的“肌肉记忆”。当时的提交说明和一份
长期维护的提交日志也由作者自己整理；这一记录
习惯延续到早期 Tinylibc，直到后来开始大量使用 agent 才逐渐改变。这里属于作者对开发方式的回顾，
这里不再用缺失的会话材料扩张 Git 能支持的结论。

SC7 始终是团队成果。后续文档引用它时，应分别标注团队能力、外部参考、提交归属、作者回忆和研究者
推断；不能因为作者延续了 Tinylibc，就把 SC7 的全部成果并入个人项目史。

作者曾使用“功能最丰富的 C 内核”并影响同届其他项目来评价 SC7。现有材料既不足以建立完整的赛事、
功能和语言对照，也没有证明其他项目的借鉴链条。因而该评价只作为待检验的作者观点保存在
[SC7 证据表](../evidence/sc7.md)，不用作本章衡量项目价值的依据。
