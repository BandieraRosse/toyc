# RF 私有动漫角色与 GPU Scene 接入

> 状态：活动
>
> 所有者：Rasterfall character art、RFCHAR 与 GPU Scene presentation
>
> 开始：2026-09-28

## 目标与范围

创作一名私有、原创的 RF 动漫角色，在造型精度上位于现有 RF Humanoid V2 与本地 Eula 样本之间。脸、头部和发型参考成熟动漫角色的造型规律，但模型、拓扑、纹理、动作及角色身份均独立创作。纹理优先服务脸部辨识、发束分层和材质分区，不以高分辨率或精细绘制为前置条件。

角色使用 RFCHAR V1 的 canonical 骨架、稳定 humanoid role 和 attachment，运行时使用 RFM2、RFANIM 与逐实例 pose。正常帧只接入 Windows 单人 GPU Scene。CPU 旧动漫绘制、Eula/Maid/PMX/VMD 正常帧恢复、联机画面及 CPU/GPU 画面对照不属于本计划。完成单人实机验收后，把 GPU Scene 设为单人默认渲染入口，同时保留显式 CPU 入口；改变默认值前不把尚未接入的角色当作已交付功能。

本计划只拥有执行顺序和完成门槛。骨架、资产与动画合同分别见[角色资产](../reference/character-assets.md)和[动画架构](../architecture/animation-architecture.md)；Scene 帧与资源所有权见[GPU 架构](../architecture/gpu-rendering-architecture.md)。

## 已知起点与技术取舍

- 现有 RF Humanoid V2 提供完整的 21-role canonical 骨架、稳定 socket、正式动作组合和 GPU Scene 蒙皮路径，可作为骨架与握枪基础；其简化脸部和头发不足以承担本角色的动漫近景表现。
- 本地 Eula RFM2 样本有 20,197 顶点、73,923 索引、213 根骨骼和 25 个材质组；材质记录包含基础纹理、toon、sphere、边线与双面标志。它仅用于技术清点与视觉研究，不作为待接入资源或顶点、骨骼、材质数量目标。
- 当前 RFCHAR GLB 输入允许基础颜色纹理、OPAQUE/MASK 和最多两项顶点权重；不直接表达完整 PMX toon/sphere/edge 语义，也不接受 morph target。材质能力需要明确的 RF 资产元数据与 GPU consumer 合同，不能依赖旧 PMX 字段的偶然兼容。
- 当前 Scene 角色路径固定 RF Humanoid V2 body，按索引逐帧打包角色几何，仅提交平色材质，并限制单网格索引数。新角色需要资源目录、材质提交和不可变数据缓存；不把 fixture 路径原样扩为正式高模路径。

首个竖切样本必须同时包含完整头部、头发、身体、简化服装、步行和持枪。暂以约 40–80 根骨骼、少量材质和小图集作为设计预算；它们是待实测的起点，不是格式上限或验收固定值。

### 2. RF 资产与动作

使用 Blender GLB → RFCHAR importer → RFM2 主链。保留 21 个必需 humanoid role、T-pose、512 RFU/m、最多两项蒙皮权重及 WEAPON_R/FOREGRIP 等稳定 attachment；头发、衣摆或袖口需要运动时只增加不破坏主骨架父链的辅助骨骼。优先以骨骼和网格处理发束运动；如果确需表情替换或 morph，先设计并验证新的资产与运行时合同，不让渲染器猜测源格式私有语义。

先制作 RFANIM idle、walk、rifle idle/aim/fire，复用 lower/upper/additive 动作语义、独立展示时钟、finalized socket 和双手握枪链。再按正常游戏需要补受击、倒地、死亡及复活。资产缺失时的展示回退只改变 presentation，不影响玩法 actor 真值。

### 3. GPU 动漫材质能力

从低精度基础纹理和材质分组开始，逐项接入 toon 明暗分档、材质边线、双面表面与少量 sphere 高光。先核对本地参考样本各通道的实际使用，再为 RF 角色定义可导出、可验证的材质语义、默认值及缺失能力反馈。脸、头发、衣服可以共享小图集；按材料需要明确 OPAQUE/MASK 与透明层规则，不让透明头发或睫毛破坏 WORLD 深度和层序。美术效果由 GPU Scene shader/材质路径消费，不调用旧 CPU 动漫渲染。

### 4. GPU 资源与高效正常帧

为角色 catalog 加入稳定资源 ID 和 Scene 只读 actor source。加载或资源版本变化时准备顶点、索引、权重、材质与纹理；逐 actor 保留独立 pose、动作历史和骨骼 palette，每帧只更新必要的动态数据，由 GPU 执行顶点蒙皮。避免每帧按三角形重建高模 bind 数据；根据实际模型拆分超过单资源索引上限的网格。准备近、中、远 LOD，保持骨架、socket、材质身份和动画相位一致，并在实机数据支持下调整绘制次数与资源复用。

### 5. 正式接入、验收与默认入口

先在隔离角色场景验证资源和动画，再接入正常单人 Outpost/Campaign Scene。Windows native 检查前后侧与三分之四近景、FPS/RTS、步行与射击、武器握持、头发双面/遮罩、边线和 toon、遮挡、LOD 切换、世界切换及多名实例。记录 GPU 蒙皮、上传、角色准备、绘制和 present 成本；性能目标以同包同场景实测和现有 GPU 标准判断，不从 Eula 规模推导固定帧率。

角色及正常 Scene 通过构建、逻辑与 GPU 提交、窗口/present 和错误传播验证后，修改单人默认 renderer 与用户说明。显式 CPU 入口继续可用；网络仍按现有范围处理，不因单人默认切换隐式进入未支持的 Scene 模式。

## 完成门槛

1. 原创源资产、manifest、导入产物和角色身份可复现；GLB contract、RFM2 runtime、骨架/附件与动作验证通过。私有源和产物按现有 private-assets 边界保存。
2. 正常 GPU 单人帧显示该角色的脸、头发、身体、动作、武器、LOD 与选定动漫材质能力；缺失能力有明确状态，不用旧 CPU 绘制补画。
3. 静态几何及纹理跨帧复用，多实例共享不可变资源且姿态互不污染；GPU skinning 和 frame lifecycle 通过实机日志验证，没有明显的加载、上传或 present 回退。
4. GPU Scene 成为单人默认入口，显式 CPU 入口和网络模式选择行为清晰；帮助、Windows 工作流、角色与 GPU 架构文档同步更新。
