# fast 楼梯边界、固定灯变化与换图修复

> 状态：历史现场，2026-10-06
> 归档原因：保存本轮修复、原生证据、性能对照及未签收边界，不作为稳定设计合同
> 当前入口：[光照架构](../architecture/gpu-lighting.md)、[原生运动与改灯指南](../guides/gpu-lighting.md#原生运动与固定灯变化)、[帧同步边界](../architecture/gpu-rendering-architecture.md)

本轮接续默认 fast 的交付：修复楼梯局部硬黑块，以真实输入检查运动和门洞，验证整图固定灯
改色/关闭/恢复，定位第三张地图失败，并检查是否保留已有性能收益。CPU 准备和同步优化仍是
后续工作；本轮补齐同帧光照准备归因，不引入跨帧在途资源。

## 原因与修复

接收缓存 BSP 原先只收紧正轴向法线的子 AABB。楼梯底面及楼板三角形的负轴向法线未收紧，
递归继续使用父范围，生成不可到达的角点和 unresolved 叶。现在两种法线符号都按半空间收紧；
新增悬空轴向楼板的正反绕序回归，检查接收样本数量和中心 HDR 一致，继续保留薄墙和有效零值断言。

换图失败由日志确认为第三张 `return_whu_planar_massing_v0.map` 的 FLOOR 有 73,390 三角形，
单层就超过建筑提取的 65,536 primitive 上限。基线和同包 reference 均曾在第 61 帧失败，
不是 fast 专属。现在从实际冻结 FLOOR 网格还原矩形，应用其局部原点，只合并严格相接、同高度、
同反射色且另一轴跨度相同的矩形，仍以每矩形两个三角形提交建筑。保留洞口及颜色边界，
可见网格和碰撞输入不变；不扩大容量、不以包围盒封住缺口。该图 FLOOR 变为 192 三角形，
建筑共 195 primitives / 228 硬件三角形。

普通光照准备现在计入 `prepare_us`，慢帧另有 `lighting_us`。之前在准备总计之后调用该步骤，
可能遗漏首次建筑/探针初始化和普通灯准备。现有上传、蒙皮批次、录制、acquire、queue、present、
retire 的计时与之一起按同一冻结帧观察；它们含嵌套区间，不能直接相加或用整帧减 GPU 推导可省 CPU。

## 真实运动与固定灯

`tools/gpu_indirect_motion.py` 使用现有 Win32/SDL 输入和实际呈现批次的 capture 请求/完成协议。
窗口必须真正获得前台焦点；隔离焦点的早期运行失败，后续在允许访问前台的原生执行中完成。
不以输入消息、坐标日志或静止画面代替真实运动。最终 fast 44 张、reference 43 张，
最大位移均约 7,932 RFU，地面高度变化 1,229 RFU；保存实际帧号、坐标、时间戳、PNG、
`motion.webp` 和 `contact.png`，目录为 `motion-reviewed-fast/reference`。

该路线包含楼梯往返、门洞对齐后穿门、相对鼠标左右转向、FPS→RTS 一层剖切，以及可见角色
走回门洞再返回 FPS。已查看两种模式的连续取样：原硬黑块恢复照明，未见持续黑屏或旧光场残留，
角色和视角武器随位置改变受光。fast 局部间接分布比 reference 平滑；高空 RTS 角色较小，
该序列不等于近景脚部接触的精细验收，也不代表所有楼梯/门洞或完整二层/屋顶路线。
早期 D 键定时越过门洞、RTS 全貌点到屋顶的尝试保留，但不作为穿门及可见角色通过证据。

新增显式 `RF_GPU_FIXTURE_SEQUENCE=90` 诊断，每 90 个冻结帧依次原灯、红灯、关闭、恢复。
通过正式固定光源 API 同时改变直接/间接输入；只在首帧、地图代际或灯阶段变化时安装，避免
每帧清空探针历史和重复预热。正常玩法、太阳/天空、曝光、灯具自发光表面不变。

两种模式分别在 Outpost 49 盏固定灯和车间 43 盏固定灯完成 360 帧，四阶段实际呈现批次齐全，
均正常退出。证据为 `fixtures-outpost-fast/reference`、`fixtures-workshop-fast/reference`。

车间 buffer 从旧 31,752,528 B 增至 94,504,016 B（约 90.13 MiB），Outpost 从 44,494,928 B
下降。收紧范围消除了大量无效分区，也改变容量试探后的布局；车间更多有效样本及更细间距是明确
成本，不能隐去。以上为每个 graphics owner 的 GPU 可见 buffer 大小，不是实测独立显存增量；

第二张行动图仍有 320 个 unresolved，任意斜面及完整几何覆盖仍需后续处理。

## 原生生命周期验证

最终 EXE 的 `tools/gpu_scene_play.ps1 -Stage World` 在 fast 和 reference 下均完成 120 帧，
30/60/90 帧三次代际切换、第三张地图及返回行动图均成功，实际退出码 0。
`world-final-fast/reference` 保存启动参数、EXE 哈希及 stdout/stderr；Khronos Core/Synchronization
validation 确认激活，无 VUID、同步危险或 validation error。首次补验因传入脚本不支持的绝对
输出路径而在启动前失败，改用仓库相对路径后完成；不把脚本参数错误算作 GPU 故障。

Windows native 构建成功；最终同版 `--logic-test`、`--gpu-lighting-test` 实际退出 0，
光照专项包括新增 `axial_winding=1`、固定灯/有效零值/薄墙/几何替换/清空/隔离/resize，
Core/Synchronization validation 无错误。证据为 `build-final.log`、`checks-final/report.json`
和对应 stdout/stderr。文档链接/UTF-8 检查与 `git diff --check` 通过；本轮未扩大到编译器测试
或 bootstrap 更新。

`capture-final-fast/reference` 各完成四个 1280×720 镜头、每镜头 8 帧 native 提交，已复查两图楼梯。
与此前相同镜头的 reference 比较并非逐像素相等：车间二层/楼梯的单通道平均绝对差最大
0.160 / 0.415（8 bit），Outpost 一层为 0.596、楼梯为 0.0022；单像素最大差分别

## 三轮同机性能

两张图各 baseline-fast、candidate-fast、candidate-reference 三轮，共 18 次普通运行。
1920×1080、同源地图/镜头/时刻/曝光，120 帧预热、240 帧采样；第二轮反转模式次序，
全部轮次保留。关闭运动/固定灯序列、截图、HDR、计数和 validation，运行期间不构建。
原始参数、逐轮分位数和 NVIDIA 采样见 `perf-r2/manifest.json`、`report.json`。
后段温度约 86–87℃并出现热限频，不能宣称严格锁频、热状态完全匹配或普适收益百分比。

下表单位 ms，每项为三个独立运行对应分位数的中位数，**不是把各轮帧合并后的分位数**。

| 车间 candidate-fast | 18.452 / 19.864 / 21.228 | 26.372 / 28.492 / 30.078 | 3.787 |
| 车间 candidate-reference | 25.224 / 26.750 / 27.208 | 33.427 / 36.797 / 40.433 | 3.824 |

本轮 fast 对同包 reference 的 GPU P50 约降低 26.8% / 39.1%，整帧约降低 21.1% / 27.4%；

**稳定整帧 60 FPS 仍未签收**。

## 同帧准备与等待观察

另跑 fast 的 `RF_GPU_SCENE_PROFILE_SLOW=1`，每图正常预热 120 帧、240 帧样本，
各保留最慢 16 帧，全部 `scene_frame == main_query_frame`，没有截图、固定灯序列或 validation。
这是单次慢帧子集观察，与上面的三轮性能对照分开；各列为所选 16 帧的中位数，不能当作
全体普通帧 P50，也不能相加各列中位数。原行在 `profile-*.stdout`，解析及范围在对应 JSON。

线程 CPU 计时只有 0/15.625 ms 等粗粒度值，本轮不以它推断精确 CPU 执行或系统抢占。
所选帧两路 AUX 没有刷新；不能用这些样本代表实际 AUX 更新帧。车间冻结阶段曾达 4.390 ms、
角色准备达 5.268 ms，Outpost layer 达 4.953 ms，说明后续还需按实际输入寻找重复准备和长尾。
retire 接近同帧 GPU 时间，体现当前单槽边界，但不证明消除等待即可省掉这些毫秒。

下一步仍先分析并减少 CPU 重复准备，核对动态上传的兼容性，再考虑把蒙皮记录并入兼容提交；
必须检查资源 reader、共享 AUX、失败取消和退休合同。只有这些工作后的配对测量确认串行依赖
成为主要限制，才另立多帧并行方案。本轮不把等待墙钟转换为承诺的 FPS 收益。
