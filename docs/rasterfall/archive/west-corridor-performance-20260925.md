# 西侧走廊按钮整波性能调查与优化建议

> 状态：历史调查现场，2026-09-25；不是性能签收
> 当前入口：[性能诊断](../guides/rendering-performance.md)、[活动计划](../plans/README.md)

## 问题与覆盖修正

用户确认默认 rasterfall.map、`--gpu-scene-play`、1280×720，在西侧宽走廊按按钮一次生成
整波敌人时约 30 FPS；自然波次逐个生成明显较轻。CPU 路径更慢，不是本次 GPU 入口误选。

原测试包含 AI/组件，但 near 0/30/60 固定 tick 不能覆盖该负载。追加 240 帧 near 诊断发现，
初始 20/30 敌人的热帧存活均值只剩约 2–5，尸体和展示来源也不等于活敌人数。
固定 tick 隐藏真实时钟补步；自然波次/自动巡游同样不能替代按钮整波。

新增 `tools/gpu_scene_old_map_perf.ps1` 和 `gpu_scene_old_map_report.py`；runtime 增加只读
SCENE-RUNTIME 时间/补步/丢弃时间/地图/相机/分辨率/AI/存活/死亡统计。新增三个 normal view
显式构造空走廊及两种按钮：先预热 60 帧，再通过正式 session 交互入口生成原有随机 16 敌人，
观察者在 `(-32000,0)` 朝西。没有将随机特感替换为普通敌人，没有禁用 AI、地图组件或碰撞。
交互使用按钮位置的诊断相机；不是 OS 鼠标点击或完整步行路线复现。

## 三轮结果

Windows native、NVIDIA GeForce RTX 3050 Laptop GPU、1280×720，18 次运行，每次 360 帧，
前 60 帧预热，三轮中第二轮反序。全部 6480 帧通过 native/零 mixed/零 bridge/零 readback
及地图输入检查。12 次按钮运行各在第 61 帧成功生成 16，测量期间持续保持 16 个活敌人。
26 AI、134 prop 输入保留；正常拉拽和击飞会改变观察者位置。

单位 ms。各指标先按一轮计算，再取三轮中位数；FPS 是每轮 `1000 / mean(interval_ms)`
再取中位数，不是瞬时 FPS 的平均。下表使用真实时钟。

| 场景 | FPS | 帧间隔 mean | P95 | P99 | 最忙线程核占用 |

| 空走廊 | 59.98 | 16.673 | 18.118 | 24.592 | 0.655 |
| 原随机按钮，16 活敌人 | 54.18 | 18.457 | 23.218 | 31.921 | 0.751 |
| 无 Tank 按钮，16 活敌人 | 53.56 | 18.670 | 22.535 | 33.848 | 0.771 |

逻辑步，测量窗口没有丢弃逻辑时间；本次不支持“逻辑补步失控是主要原因”的结论。

按键次数及局部近景仍可能改变成本。不能用本次 53–54 FPS 否定用户现场。

GPU 时间与 CPU 墙钟重叠，不能相加；资源更新包含验证、复制、map/flush 及适用的 transfer，

这些成本不会因西侧战斗中看不到多数地图 AI 自动消失。

## 是否单线程瓶颈

`rf_game_runtime_run` 在同一调用链串行执行逻辑、来源/冻结/pose、Scene prepare 和 submit/retire。
`enemy_draws_prepare` 逐身体提取、验证/上传，未启动并行 worker。操作系统采样显示两种按钮
进程总 CPU 核占用约 0.817/0.828，最忙线程约 0.751/0.771；绝大多数 CPU 时间集中在一个线程。
采样排除初始加载、重复末帧和 teardown；采样核占用不是整机任务管理器百分比，也未把最忙
线程通过 OS 标识为 main thread。

结论是 CPU 串行准备与同步依赖是主要优化方向，当前 GPU draw 并未占满 16.67ms 帧预算。
但本次不能声称 CPU 单核始终 100%，或仅靠加线程就能解决；仍有 GPU 等待、驱动、帧调度和
跨阶段依赖。GPU draw timestamp 不覆盖之前的全部上传/蒙皮，不能说整个 GPU 只工作约 2ms。

## 优化建议（尚未实施）

1. **消除不变地图的 V1 重烘焙。** 当前 floor freeze 每帧扫描所有 primitive；由地图/光照 owner
   按有效输入或 generation 持有缓存，切图/重载/相关几何变化失效，帧冻结只复制只读结果。
   验证相同地图重新 bake、world cycle 及展示模型画面。收益上界是整个 freeze 约 1.4ms，
   V1 本身尚未独立计时，不承诺完整收回 1.4ms，更不能把它说成帧率减半主因。
2. **在 pose/几何/上传前做保守可见性裁剪。** 程序 AI collector 当前直接遍历全部活动 AI；
   敌人来源主要做远距判断，没有完整身体视锥剔除。优先避免走廊画面外的身体逐帧求值和上传，
   不停止玩法 AI。身体、装备、阴影、舌头、死亡运动分别用保守 bounds；不可跨过可见附件而误剔除。
   无敌人仍有角色准备约 3.2ms、程序几何/更新约 3.7ms，说明基础成本值得优先处理，
   但这些总值不是可保证全部消除的收益。
3. **降低动态网格展开和更新成本。** 当前逐三角形展开为 56 字节顶点、逐顶点 V2 查询，再逐资源
   验证和 map/copy。保留拓扑/索引和不变字段，用唯一顶点或紧凑 Scene 顶点；按姿态和世界光照
   输入拆开失效范围；GPU 蒙皮/刚性实例变换替代可移出的 CPU 展开。正确性检查可拆成资源创建时
   不变量与每帧动态范围检查，不能直接删除 preflight。每步比较三角形、画面、字节和 CPU 耗时。
4. **准备完成后再处理提交流水。** 批量上传、持久 staging/map、slot 退休后复用，并评估双 slot
   让上一帧 GPU 与下一帧 CPU 工作重叠。必须维持 pin/generation、透明层顺序和故障关闭合同；
   不通过删 fence 或过早复用正在被 GPU 读取的内存换速度。
5. **按测量推进并行与 AI 优化。** 几何并行前，拆掉共享 renderer 全局/scratch，使任务只读冻结
   快照并持有私有工作区，按稳定来源顺序合并；不要直接给当前循环加线程。AI 本次约 1.3–1.5ms，
   暂不是第一优先级；更高负载若证实 ground/collision/LOS 的全 primitive 扫描主导，再做空间索引
   和缓存，保留确定性结果，不降低逻辑频率。

每个改动在同包受控对照之外，必须重跑 Corridor 的真实时钟三轮，并核对活敌人数量、种类、
尸体、AI、组件和相机范围；需要新增按钮随机 seed/移动开火路线时单独记录负载，不能混合统计。
诊断目标先让整波平均帧时间回到 16.67ms 内、显著降低 P95/P99；最终仍按正式性能标准签收。

## 高负载续查：32/64 敌人

2026-09-25 按用户要求追加。以上三轮结果属于旧的 **16 敌人** 现场；本节为新构建的独立
测量，不能直接当作算法优化前后对照。本次已稳定复现高负载低帧率，修正此前覆盖不足。

### 复跑与覆盖

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/gpu_scene_old_map_perf.ps1 -Stage Corridor -OutputDirectory tmp/corridor-high-20260925
```

输出目录必须不存在。Corridor 默认改为 32、64 档；`-CorridorEnemies 16` 保留原单次按钮
测试。按钮 view 的 CLI 敌人数表示第 61 帧请求生成的总数，0 兼容旧的 16；不会再提前在
near 区域放置这些敌人。预热后连续调用 2/4 次正式 session 按钮交互，每次仍生成原有随机
16 个敌人。没有改正式按钮、随机池、HP、AI、碰撞、玩家受击或死亡规则，也不模拟人工按键间隔。

Windows native、RTX 3050 Laptop GPU、1280×720；同包 30 次，每次 360 帧、前 60 帧空预热，
三轮、第二轮反序。10,800 帧全部通过 native/零 mixed/零 bridge/零 readback 检查；9,000 个
热帧全部处于未暂停 PLAYING。每帧保留 26 AI、134 prop 输入；地图日志为 922 个 primitive。
每个按钮运行均在第 61 帧生成所请求人数，预热存活数为 0；六种敌人数之和与存活数逐帧相符，
无 Tank 池的 Tank 数始终为 0。

统计仍逐轮计算后取三轮中位数；FPS=`1000/mean(interval_ms)`。每轮保留 61–360 帧，
含首次按钮的资源开销；报告新增每 100 帧窗口、逻辑总时间/总 tick、种类与相机范围。
这是带日志、外部采样的诊断，不是低扰动产品验收。首轮空走廊 realtime 为 55.86 FPS，后两轮
59.76/59.96，说明环境长尾仍存在；不把小幅波动解释为代码收益。

### 耗时归因与变化后的优先级

以下为 realtime 分段均值的三轮中位数，单位 ms；GPU draw 与 CPU 时间重叠，不能相加。

| 分段 | 空走廊 | 原 32 | 无 Tank 32 | 原 64 | 无 Tank 64 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 逻辑（帧内全部 tick） | 0.107 | 2.359 | 2.368 | 18.164 | 6.134 |
| freeze | 1.458 | 1.403 | 1.367 | 1.341 | 1.378 |
| 模块化角色准备 | 3.224 | 3.323 | 3.535 | 4.380 | 3.916 |
| 敌人/程序角色几何 | 1.990 | 3.781 | 4.778 | 6.060 | 7.159 |
| 敌人/程序角色资源更新 | 1.727 | 3.410 | 5.020 | 9.179 | 8.984 |
| 退休等待 | 4.704 | 2.770 | 3.250 | 7.193 | 5.560 |
| GPU Scene draw | 2.071 | 2.182 | 2.566 | 6.170 | 4.723 |
| 每帧逻辑步数 | 1.003 | 1.240 | 1.447 | 2.790 | 2.180 |

1. **动态几何/更新仍是持续成本。** 64 档几何与资源更新合计约 15–16ms；每帧总上传约
   11.66/13.45 MB，路径三角形约 65,342/76,031（均含程序角色）。无 Tank 并不等于低几何量。
   `enemy_draws_prepare()` 串行提取各身体，`scene_enemy_triangle()` 逐面展开并查询/缓存顶点光照，
   `rf_gpu_graphics_triangle_resource_update()` 逐顶点验证并 map/copy，必要时还执行 transfer。
   现有计时不能进一步区分验证、内存复制、驱动或 transfer 各自占比，也不能称为纯总线瓶颈。
2. **高负载必须提高逻辑尖峰的排查优先级。** 原 64 每轮丢弃逻辑时间约
   1116.689/1133.356/1266.692ms，无 Tank 为 583.345/250.005/250.005ms；fixed 均为 0。
   原 64 首轮第 199 帧逻辑 127.030ms（3 tick），后续连续触达 4 tick 上限。
   第三轮 161–260 帧仍平均 60.15 活敌人，FPS 15.95，平均 3.2 tick，每 tick 逻辑 8.033ms。
   因此既有单步成本变化，也有慢帧后补步放大；不是仅增加相同成本的 tick。
   当前 `logic_us` 覆盖整个 runtime update，不能全部称作敌人 AI 时间。
3. **下一层具体计时点已明确，但还没有函数级占比证据。** `nav_next_waypoint()` 每次建立 BFS
   工作区并回溯可通行路径；`toy_game_query_ground()` 与碰撞查询扫描 primitive；
   `separate_enemies()` 遍历活敌人配对，重叠时再调用碰撞检查。64 人有效配对数为 2016，
   32 人为 496，但这只是复杂度依据，不是实测主因。应先分别计时导航、移动/地面、特感、分离
   和队友更新，再决定索引或缓存；保持确定性、碰撞语义和逻辑频率。
4. **freeze 不是本次扩展成本的主导。** 它在各档仍约 1.3–1.5ms。V1 缓存仍有价值，但不能
   用它解释 64 敌人下的 37–50ms 帧间隔。可见性裁剪及紧凑动态顶点仍应与逻辑排查一起推进，
   随后才按证据评估批量上传、同步流水及并行工作区。

64 档最忙线程核占用中位数约 0.788/0.764，仍不能宣称单核持续 100%。GPU draw 已增长至
约 4.7–6.2ms，退休等待也增长；不能沿用 16 人时“draw 约 2ms”的数字，也不能把退休等待
当作 present API（本轮 API 均值仍约 0.11–0.12ms）。GPU timestamp 仍不覆盖全部上传/蒙皮。
