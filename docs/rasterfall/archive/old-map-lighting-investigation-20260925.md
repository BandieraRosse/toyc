# 旧地图光照与少量敌人性能调查

> 状态：历史调查现场（2026-09-25）；不代表产品 FPS 签收或根因已全部定位
> 当前入口：[性能诊断](../guides/rendering-performance.md)、[光照架构](../architecture/static-world-lighting.md)

## 覆盖核对

用户报告无敌人接近 60 FPS、少于 30 敌人约 30 FPS。启动方式和镜头尚未确认，
本次按默认 Campaign `rasterfall.map`、独立 Scene 排查。

既有 `gpu_scene_cost.ps1` 并非空地图：历史原始日志加载 Campaign，包含 134 个 prop 输入、
near 镜头 57 个 prop draw、8 名模块化队员及 18 个程序角色。密集组件测试还将组件移入镜头，
保留 134 个 object 和 128 个 prop draw。因此不能把问题概括为漏掉 AI/组件。

但原生固定场景 CLI 原先只接受 0/30/60 敌人，缺少低敌人数档位；本次只扩展诊断输入为
10/20，并同步 help。成本 A/B 汇总工具仍保持原有矩阵。固定测试每帧只跑一次 16ms tick，
实玩按 elapsed/accumulator 补步，且镜头、死亡和特效负载会变化；两者不能等同。

## 光照发现

`rf_game_runtime.c` 每个 Scene 帧调用 `rf_gpu_scene_world_floor_freeze`，后者无条件调用
`rasterfall_diagnostic_world_light_bake_v1`。V1 对 32×24 个采样点各遍历全部地图 primitive，
即使地图未变、没有敌人也重复执行。旧 renderer 的 `prepare_diagnostic_world_light_v1`
反而有 ready 缓存。这是 Scene 接入展示模型时遗留的重复 CPU 工作，尚未修复。

正常 V2 bake 在 world 加载/切换时执行；动态敌人和程序角色仍在 CPU 提取中逐顶点查询
V2 field（带精确坐标缓存），然后完整更新动态顶点。不能把 V1 重烘焙、V2 查询、
form lighting、几何生成及上传统称为同一光照开销。

本次没有关闭光照消融，也没有单独计时 V1；只能用包含 V1 的整个 freeze 阶段作为上界。
不能据此证明 V1 是 60→30 FPS 的主因，或证明逐顶点 V2 成本可以忽略。

## 本次原生补测

Windows native required GPU、独立 Scene、默认 1280×720，工具选择 NVIDIA；沿用正常资产。

所有轮次均通过脚本的连续 native 帧、零 bridge/readback/mixed execute 与来源数量检查。
无敌人仍处理 26 个角色实例及 23100 个敌人/程序角色路径三角形。
20/30 档热帧来源均值为 19.75/29.58，战斗导致少量尸体过期，不能称每帧恒定存活人数。
GPU Scene draw 均值约 0.37–0.68 ms；不能与 CPU 墙钟相加。

固定 near 未复现约 30 FPS。随敌人数增加的主要可见增量在 CPU 几何/动态上传和逻辑，
freeze 约 1.3–1.4 ms，基本不随敌人数变化；等待减少吸收了一部分 CPU 增长。
等待根因和实玩下降仍需按用户实际入口、镜头及真实时钟核对，不能仅用本表排除用户现象。

证据位于本地 `tmp/old-map-investigation-20260925/r1-*`、`r2-*`，各轮含原始日志和 executable hash；
`summary.json` 保存热帧 mean/median/P95/P99。初次原包试跑的 `10/` 是 CLI 拒绝日志，
不纳入测量；`0/` 是重新构建前的单独试跑，也不纳入表格。

本次修改仅补诊断敌人数与文档，没有改动光照或渲染算法。后续应先消除静态 V1 重烘焙，
再分别测量动态光照、几何和上传，补真实时钟及多镜头低敌人数验证。
