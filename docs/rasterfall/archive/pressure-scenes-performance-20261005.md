# 多层建筑与枪手压力场景性能调查

> 状态：历史
> 调查日期：2026-10-05
> 归档原因：保存一次性能调查及初步建议，不作为当前架构或性能签收
> 当前入口：[性能诊断](../guides/rendering-performance.md)、[GPU 性能标准](../reference/gpu-performance-standards.md)

当前压力场景的优先热点是感染体及展示几何生成、模块角色准备、动态上传和同步提交链。
多层建筑的静态 WORLD 准备成本相对较小，但建筑背景同时增加阴影、动态图层和玩法碰撞负担。
枪手需要分别观察角色 AI 和角色渲染，不能将新增枪手后的整帧增量全部归为 AI。
以下优化顺序是本次调查建议，尚未实施，也不替代唯一活动计划。

## 初步优化顺序

1. **减少感染体和展示几何的重复生成及上传。** 首先针对 3.7–4.8ms 的几何生成段，拆开稳定拓扑、
   配色、根变换和动画输入；优先复用局部几何，让根移动和刚性肢体变换由 GPU 消费小型参数。
   当前完整冻结值的 `memcmp` 缓存会被移动或姿态变化打破，容量保留已经存在，单纯再加一个完整帧缓存
   收益有限。先做一种感染体家族的等价原型，保持身体、特感附属、死亡透明和主视图/阴影的实际内容。
2. **拆分角色准备长尾，并扩展已知容量的复用。** 单独统计 body、附件、武器、palette、资源创建和
   蒙皮提交等待，按创建/更新/复用分类。对会重复出现的身体及死亡表现保留必要容量，优化实际失效键；
   继续保持 world/source 身份校验及全部 reader 退休合同。首图已有六份枪手资源备用池，本轮入口日志
   `ready=6 missing=0 failed=0`，不能把“增加六名枪手预热”再次当成新方案。
3. **缩小建筑碰撞与跨层试走的候选集合。** 当前普通地面/身体查询仍可能扫全图图元，已有导航
   sweep 候选仅在单次同步探测中生效。考虑静态空间桶和高度区间宽相查询，返回原图元顺序的保守候选，
   保留正式支撑、楼板厚度、身体和落地规则。继续使用确定性工作配额；同时测规划等待步数和多角色排队，
   不能只减少单步耗时而增加不可见的命令等待。
4. **减少提交及同步断点，再评估多帧 pipeline。** 当前每帧先同步完成蒙皮，提交主帧后立即退休，
   完整场景退休墙钟约 6.3ms。先减少重复上传、合并兼容提交，补 GPU 分段时间戳区分蒙皮、阴影、
   主绘制和后处理。跨帧双缓冲会改变资源、query、swapchain、取消帧及多视图生命周期，属于后续较大
   架构工作，不能直接假定能省掉全部退休时间。

第一轮实现宜先选感染体几何或角色准备中的一个热点，使用同 exe/资产、固定窗口、相同实体规模的
五轮 AB/BA 对照，复用已新增五人跨层路线，并补正式首图反击阶段采样。没有测得独占场景收益前，不调整玩法真值、
删除可见内容或仅靠降低渲染分辨率宣称问题解决。
